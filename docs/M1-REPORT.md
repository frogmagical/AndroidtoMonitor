# M1 実測レポート

**Status: v1.0 FIXED**(2026-08-14 実装・実測、レビュー済み。判定: 条件付きPASS。commit 2a4743b の実装内容 + E2E遅延実測の追加分)

## 1. 実施内容

M0で保留となっていた「E2E p95 ≤ 100ms」の実測を、M1受信アプリ(commit 2a4743b)を使って行った。M0-REPORT §6の申し送り通り、M1は到着フレームを即時デコード投入・即時描画するため、正しく計測できればログの値がそのままパイプラインの実遅延になる。

## 3. 計測方式

### 3.1 追加した計測項目

`TcpServer.kt` のvideoフレーム受信完了時に、既存の `recvTimeNs`(モノトニック、recv→render計測用)に加えて `recvEpochUs = System.currentTimeMillis()*1000`(端末のWall Clock)を同時刻に取得。`PerfStats.recordPtsToRecv(ptsUs, recvEpochUs)` で `(recvEpochUs - pts_us)` を1秒毎にp50/p95集計し、A2M_PERFログに `ptsToRecvP50ms` / `ptsToRecvP95ms` として追加出力(生値、PC/Android間のクロックオフセットを含む)。

### 3.2 クロックオフセット較正 (`tools/m1/clock_offset.py`)

`adb shell date +%s%N`(toybox、`%N`ナノ秒対応を確認済み)をブラケット法で50回実行:
- PC側送信直前時刻 `t0`、応答受信直後時刻 `t1` を記録
- 端末が時刻をサンプルした瞬間を `(t0+t1)/2` と仮定(NTP式ブラケット法。adb往復の遅延が概ね対称という前提)
- `offset_us = 端末epoch - PC中央値epoch` を全50サンプルで算出し、**中央値**を採用(外れ値に頑健)
- 不確かさは **min(RTT)/2**(往復遅延が最小だったサンプルが最も歪みが少ないという前提)

### 3.3 E2E算出方法 (`tools/m1/measure_e2e.py`)

1. logcatの `A2M_PERF` 行を1秒バケット単位でパース、`frames=0` のバケット(無通信時のプレースホルダ0.0)は除外
2. バケット毎のp50/p95系列から、全体のp50/p95を **p50=バケットp50系列の中央値、p95=バケットp95系列の95パーセンタイル** として算出(「パーセンタイルのパーセンタイル」。1秒集計ログしか無いため生の全フレームpercentileは算出不可 — §6の既知の限界を参照)
3. `ptsToRecv補正値 = ptsToRecv生値 - クロックオフセット(較正前後の平均)`
4. `E2E(送信刻印→描画) = 補正済みptsToRecv + recvToRender` のp50/p95をそれぞれ加算

## 5. 分析と合否判定

補正後の値が**負**になっている(物理的にはあり得ない、受信は送信より後でなければならない)。これは実際の伝送遅延が非常に小さく、クロックオフセット較正の不確かさ(±21〜30ms、adb shellプロセス起動オーバーヘッドが支配的)の中に埋もれてしまっていることを意味する。

- recvToRenderの実測(11〜15ms、オフセット問題のない直接測定)から、**デコード〜描画自体は十分高速**であることは確実
- ptsToRecv(ネットワーク伝送を含む区間)は、較正の不確かさが実際の信号(推定で一桁〜十数ms程度)より大きいため、この較正手法では正確な正の値として分離できなかった
- **保守的な上限見積り**: 伝送遅延は因果律により0以上なので、`0 <= 伝送遅延 <= 補正後p95 + 不確かさ ≈ -8.9 + 29.9 ≈ 21.0ms` と束縛できる。これを使うと
  `E2E p95 上限 ≈ recvToRenderP95(14.8ms) + 伝送遅延上限(21.0ms) ≈ 35.8ms`
- この上限見積り(約36ms)でも要件の100ms gateに対して約3倍近い余裕があり、**M1が計測すべき受信側パイプラインの遅延(伝送+デコード+描画)が100msを大きく下回ることは高い確度で言える**
- **レビューノート(Fable)**: 上式は伝送遅延上限の算出にE2E補正後p95(-8.9ms、recvToRender p95を既に含む)を使っており、その後recvToRender p95を再加算しているため二重に保守的。正しくは `伝送遅延上限 = ptsToRecv補正後p95(-23.7) + 不確かさ(29.9) ≈ 6.2ms`、したがって `E2E p95 上限 ≈ 14.8 + 6.2 ≈ 21ms`。いずれの計算でも判定は変わらない(むしろタイトな方が余裕が大きい)

### 判定(案): **条件付きPASS**

| 合否基準 | 結果 |
|---|---|
| E2E p95 ≤ 100ms | **PASS(推定)** — 点推定は測定ノイズにより不定(負値)だが、保守的上限(約36ms)でも要件を大きく下回る。**より正確な正の実測値を得るには較正手法の改善が必要**(§6) |

条件: この判定は「較正手法の不確かさを踏まえた上限見積りによる合格」であり、adb往復オーバーヘッドに依存しない高精度な較正(またはより直接的な計測手法)による再測定が望ましい。ただし現時点で100ms gateを脅かす要素は観測されておらず、M2(送信側実装)へ進むことをブロックする理由はないと判断する。

## 6. 既知の限界

1. **クロックオフセット較正の精度がadb shellのプロセス起動オーバーヘッドに律速される**(min RTT 43〜60ms、不確かさ±21〜30ms)。実際の伝送遅延(一桁〜十数ms程度と推定)より粗く、正の実測値として分離できなかった。改善案: 常駐シェル(`adb shell`を単一セッションで保持しパイプ経由で複数回叩く)でRTTを削減する、または映像フレーム自体に検証用タイムスタンプを埋め込み光学的に測る(M0のブラケット法に近い手法)などが考えられる
2. **1秒集計ログからの「パーセンタイルのパーセンタイル」近似**: PerfStatsは仕様通り1秒毎の集計のみを出力するため、60秒分の生フレーム毎の値をプールした厳密なp50/p95ではなく、バケット単位の中央値/95パーセンタイルで近似した。将来的に生ログ(デバッグビルドのみ等)を追加すればより正確な分布が得られる
3. PC送信側pts_us刻印はPCのローカル時計(NTP同期状態は未確認)に依存。今回のPCが大きくNTPからずれていた場合、較正で求めた「PC-端末間オフセット」自体は影響を受けない(較正もPC時計基準で行っているため相殺される)が、EPOCH時刻の絶対値の信頼性そのものはPCのNTP状態に依存する
4. 今回の映像内容(clock_overlay.ps1、低motion)はビットレートが8Mbps上限まで到達しておらず(実測1.0〜1.3Mbps)、高ビットレート・高motion時の挙動(帯域飽和時のドロップ挙動等)は未検証
5. 8時間連続動作等の安定性はM1のスコープ外(M3で実施予定)
