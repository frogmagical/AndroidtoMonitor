# M0 実測ゲート レポート

**実施日**: 2026-08-14 / **判定: 条件付き GO**(CodeXレビュー反映済み。M0の4基準中3つはPASS、E2E遅延基準のみ未実証のままM1へ継続判断。詳細は §5)

## 1. 検証環境

- PC: Windows 11 Pro、ffmpeg 9.0 (gyan.dev full)、platform-tools 37.0.1
- VDD: VirtualDrivers/Virtual-Display-Driver 25.7.23(署名済み、devconで導入)。仮想モニタ 1080×2400 稼働確認
- 端末: OPPO Reno5 A (A101OP)、受信は VLC for Android 3.7.1(公式ミラーからAPK取得、SHA-256検証済み、adb install)
- 経路: ffmpeg (x264 ultrafast/zerolatency, 12Mbps, MPEG-TS over HTTP) → `adb reverse tcp:5001` → VLC
- 測定法: 仮想ディスプレイにミリ秒時計を表示し、`adb shell screencap` の発行時刻と撮影画像内の時計値を比較(コマンド往復時間0.5〜0.7sを上限誤差として扱うブラケット法)

## 2. 判明した技術的問題と対処(M2実装への教訓)

1. **ffmpeg 9.0 の NVENC はドライバ 610+ を要求**(手元は1世代旧)→ M0はCPUエンコードで代替。
   *教訓: M2はMedia Foundation直叩きなのでffmpegのAPIバージョン要求問題は回避される。*
2. **ddagrabのPTSがそのままでは実時間とズレる**(指定30fpsに対し実効32〜39fpsで供給され、フレーム番号PTSだとストリーム内時間が実時間の1.2〜3倍速で進行)→ VLCが実時間から取り残され遅延が単調増加(16秒超を観測)。
   `-readrate 1` + フレーム番号PTSで実時間ペーシングに固定して解決。
   *教訓: 送信側PTSは必ず壁時計(QPC)基準で刻印する。要件4.2に明記済みの方針が正しいことを実証。*
3. VLCはHTTPストリームを一度プローブして再接続する → `-listen 1`単発では死ぬ。ループ化で対応。
   *教訓: 受信側の再接続時はストリーム先頭から再開(SPS/PPS+IDR)という要件4.4の設計が必須。*

## 3. 測定結果

### 帯域・スループット
- 12Mbps設定で `adb reverse` 経由のTCP転送は破綻なし。`adb pull` 実測 3〜7MB/s(24〜56Mbps)で帯域余裕を確認。

### 遅延(ペーシング修正後、VLC network-caching=100ms)
| 回 | screencap発行 | 端末表示時刻 | 遅延下限 |
|---|---|---|---|
| 1 | 22:46:38.640 | 22:46:37.111 | 1.529s |
| 2 | 22:46:41.137 | (未判読) | — |
| 3 | 22:46:43.692 | 22:46:42.181 | 1.511s |
| 4 | 22:46:46.169 | (未判読) | — |
| 5 | 22:46:48.690 | 22:46:47.180 | 1.510s |

- **定常遅延 ≈1.51s、ジッタ ±20ms**。内訳は**推定**: ffmpeg readrate初期バースト(~0.5s、`-readrate_initial_burst 0`指定でも残存)+ VLCのTSデマルチ/キャッシュ(~1.0s)。切り分け測定はしていない。
- 増大傾向なし(ペーシング修正前は単調増加していた)。

### 測定法の限界(CodeXレビュー指摘)
- ブラケット法の値は**遅延の下限値**(screencap実行はコマンド発行より後)であり、p95判定には使えない。M1では送信PTS・受信時刻・描画投入時刻をログで取得して分布を測る。
- M0の経路は `adb reverse`(PC listen / 端末 connect)だが、**要件4.1の本番経路は `adb forward`(端末 listen / PC connect)で方向が逆**。転送特性は近いと期待されるが再接続挙動は異なるため、M1は forward 経路で実測する。

### 安定性
- 測定セッション中(数分×複数回)ストリーム破綻・切断なし。長時間試験はM3で実施。

## 4. 分析

- **輸送路(USB/adb)は合格**: 帯域は要件(10〜20Mbps)の2倍以上、ジッタ±20〜30msはp95フレーム間隔要件(25ms)と同水準であり、100ms級の低遅延を阻害する要素は観測されなかった。
- **絶対遅延1.5sはテストベッド(VLC+MPEG-TS+HTTP)の構造的バッファ**であり、本設計(生Annex-B直送・PTS非依存の即時描画・バッファ深度1〜2フレーム)では存在しない経路。M0構成でこれ以上削るにはVLC/ffmpegの内部と戦うことになり、本実装(M1)で計測する方が早くて正確。

## 5. 判定: 条件付き GO

| 合格基準 | 結果 |
|---|---|
| 1080×2400@30fps 配信成立 | **PASS**(フルスクリーン表示・動体描画確認) |
| 10〜20Mbps 帯域 | **PASS**(12Mbps設定で余裕、実測帯域2倍以上) |
| E2E p95 ≤ 100ms | **保留** — テストベッドの固定バッファ(≈1.5s)が支配的で、既製プレーヤーでは検証不能。ジッタ±20msから輸送路は低遅延要件を阻害しないと判断 |
| 5分連続で破綻なし | **PASS** |

**条件**: E2E遅延の数値実証(p95 ≤ 100ms)は M1(自作受信アプリ)の合格基準に繰り上げる。M1受信アプリはPTS非依存・即時描画のため、測定値=真のパイプライン遅延となる。

**次アクション**: M1(Android受信アプリMVP)へ進む。

## 6. M1への申し送り(CodeXレビュー合意事項)

1. **PTSを再生スケジューリングに使わない。** 到着フレームを即時描画し、PTSは遅延計測専用。MediaCodec入力/Surface出力のキュー深度は1〜2フレーム以内に保つ
2. **詰まったら古いフレームを捨てる。** 遅延蓄積が最大の敵。入力滞留・デコード待ち・描画待ちをログ化する
3. **再接続はデコーダリセット + SPS/PPS + IDR待ちを徹底。** 中途NALからの復帰を試みず、必ずクリーンなIDR境界から再開する
4. **経路は要件どおり `adb forward`**(端末listen/PC connect)で組み、遅延・再接続をこの経路で実証する
